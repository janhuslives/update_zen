# 3f23a06 — Deploy diagnosis: shell alias was shadowing the real fix

## Background

After landing the ghcr version-tag fix (`437a221`), deploying it to the
`derek@192.168.7.223` server turned into a multi-round debugging session:
the fix kept "not taking" even after the file on disk was repeatedly
confirmed correct.

## Root Cause

This server had **three separate copies** of `update_zen.py` in play,
and two different lookup paths for the `update_zen` command:

1. `~/update_zen.py` (`/home/derek/update_zen.py`) — updated by `scp`,
   confirmed correct via `grep` early on.
2. `/usr/local/bin/update_zen` — meant to be a bash wrapper generated by
   `update_zen install` (`exec python3 <script_path> "$@"`, plus a
   `sudoers.d` NOPASSWD rule scoped to this exact path). An old deploy
   habit carried over from another project (`scp x; ssh "sudo cp x
   /usr/local/bin/x"`) **overwrote this wrapper with raw Python source**,
   breaking the NOPASSWD sudo chain (the sudoers rule only matches the
   literal command `/usr/local/bin/update_zen`, not
   `python3 /usr/local/bin/update_zen`).
3. `/opt/update_zen/update_zen.py` — a third, independent copy that
   turned out to be the one that actually mattered: the shell had

   ```
   update_zen is aliased to `python3 /opt/update_zen/update_zen.py'
   ```

   Bash resolves aliases *before* `$PATH` lookup for interactive
   commands, so every plain `update_zen` invocation ran this file —
   never `~/update_zen.py`, never the `/usr/local/bin/update_zen`
   wrapper. All of the `scp`/`cp`/reinstall work in earlier rounds
   was correct but landed on files nothing was actually reading.

The giveaway was `_VERSION` (bumped to `"2026-08-25a"` in this commit
specifically to serve as a deploy fingerprint): `sudo python3
~/update_zen.py install` printed the new stamp directly, proving
`~/update_zen.py` and the reinstalled wrapper were both correct — yet
running plain `update_zen` in the same shell still printed
`"2026-05-19a"`. `hash -t update_zen; type -a update_zen` in that shell
surfaced the alias and confirmed it, not `$PATH` order or bash's command
hash cache, was the culprit.

## Cleanup recommendation

Three copies of the same script and two competing resolution paths is
a standing trap — the next deploy is just as likely to hit this again.
Pick **one** canonical location and delete the others:

- **Keep `/opt/update_zen/update_zen.py`** as the single source of
  truth — it's what the alias (and therefore muscle memory / any
  existing cron jobs or scripts referencing `update_zen`) actually
  resolves to today. Changing that expectation is more disruptive than
  standardizing on it.
- **Delete `/usr/local/bin/update_zen`** (the wrapper) and
  **`/etc/sudoers.d/update_zen`** (the NOPASSWD rule tied to it), since
  neither is on the path the alias uses. Keeping a dead wrapper around
  is exactly what caused this confusion — a future `install` re-run
  would silently regenerate it pointing at whatever `__file__` happens
  to resolve to at that moment, reintroducing a fourth divergent copy.
- **Delete `~/update_zen.py`** once `/opt/update_zen/update_zen.py` is
  confirmed current — it was never the file actually executing.
- Going forward, the deploy command is just:
  ```
  scp update_zen.py derek@192.168.7.223:/tmp/update_zen.py && ssh derek@192.168.7.223 "sudo cp /tmp/update_zen.py /opt/update_zen/update_zen.py && rm /tmp/update_zen.py"
  ```
  (via `/tmp` since `/opt` is root-owned). No `install` step needed for
  routine updates — that command only matters if the wrapper/sudoers
  path is kept around; if it's removed per above, `install` becomes
  unnecessary for this server entirely, since the alias invokes `python3`
  directly and update_zen's own `main()` already self-elevates via `sudo`
  on every run.
- If passwordless sudo for `update_zen` is still wanted, either update
  the alias to point at a wrapper for `/opt/update_zen/update_zen.py`
  and re-run `install` from that location (so `__file__` resolves
  correctly), or add a `sudoers.d` rule scoped to
  `python3 /opt/update_zen/update_zen.py` directly.

None of this required a code change — it's entirely a server-side
deployment/aliasing cleanup, tracked here since it cost most of the
round-trip time on this fix.

## Addendum — cleanup executed (2026-08-25)

Ran the cleanup, with one deviation from the default recommendation
above: chose to **keep** passwordless sudo rather than delete the
wrapper, so the wrapper was re-pointed instead of removed.

1. `ssh -t derek@192.168.7.223 "sudo python3 /opt/update_zen/update_zen.py install"`
   — re-ran `install` from the canonical path. This regenerated
   `/usr/local/bin/update_zen` as `exec python3
   /opt/update_zen/update_zen.py "$@"` and rewrote
   `/etc/sudoers.d/update_zen`'s NOPASSWD rule to match (the rule text
   itself is unchanged — it was always keyed to the wrapper path, not
   the script path — but the wrapper it now guards finally points at
   the right file).
2. Verified over SSH that the wrapper's `exec` line and the sudoers
   file both looked correct.
3. `ssh derek@192.168.7.223 "rm ~/update_zen.py"` — removed the stray
   copy that the alias had made irrelevant all along.
4. Verification hit one false alarm: `ssh derek@192.168.7.223
   "update_zen"` failed with the same
   `Error: config.json is encrypted; cannot prompt for master password
   in non-TTY mode.` seen earlier in this saga. That's expected —
   a plain non-interactive `ssh host "cmd"` has no TTY for the
   interactive TUI's master-password prompt, unrelated to sudo or to
   the deploy itself. Confirmed correctly instead from an interactive
   persistent session, where `update_zen` reports `2026-08-25a` and
   runs with no sudo password prompt.

End state: `/opt/update_zen/update_zen.py` is the single canonical
copy. Both the alias and the `/usr/local/bin/update_zen` wrapper now
resolve to it, so either lookup path lands on the same file.
`~/update_zen.py` no longer exists.
